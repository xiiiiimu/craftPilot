# CraftPilot Agent 评测与性能测试方案

2026-11-21

## 目标与原则

用同一套固定数据，先测出改动前的基线，再修问题、复测，用前后对比的数字证明改进。评测同时看四件事：结论对不对（质量）、跑得快不快（效率）、花了多少钱（成本）、稳不稳（可靠性）。只看其中一项，很容易用另一项的恶化换来表面改进。

- **先测再改**：会让指标失真的问题（见"先改什么"一节的 P0）先修；其余问题先测出基线，再改，这样才有"提升了多少"的故事。
- **固定一切变量**：数据集、提示词版本、模型名、温度、工具定义、评测脚本都带版本号。改一个变量，测一次。
- **离线和在线分开**：离线用桩模型，结果确定、不花钱，测系统本身的开销和正确性；在线用真实模型，只跑小样本，测质量和真实成本。两类结果分开报告，不混在一起算。
- **控制花费**：设计文档定的预算目标是每月 ¥300，在线评测每轮设硬上限，超了就停。
- **数字必须可复现**：每次评测输出原始明细（每个 Run 一行）和汇总，并记录机器配置和数据规模。

## 现状盘点

设计文档 `docs/architecture/agent-evaluation.md` 定了完整的质量和性能指标，但实际只做了"能不能跑通、会不会出错"的通过/失败检查，没有一个质量或性能数字被实测过。`R5EvaluationHarnessTest` 是 7 个场景的开关式检查，用的是桩模型。

| 项目 | 设计文档的要求 | 实际状况 |
| --- | --- | --- |
| 观点提取 | Issue macro-F1 ≥ 0.80，需标注样本和混淆矩阵 | `OpinionExtractor` 是关键词规则，置信度写死 0.82；没有标注集，未测 |
| 反馈归因 | 模糊归因 ≥ 85% | 未测 |
| 检索 | RAG Recall@K | 未测，只验证了租户和版本过滤 |
| Agent 结论 | 引用有效率、每项主张有证据比例 | 只检查"引用的 ID 存在"，不检查结论是否正确 |
| 效率 | p95 延迟、取消确认时延 | 未测 |
| 成本 | 每轮调用成本、月度 ¥300 | 账本里有数据，但单价写死，没有汇总 |
| 数据集 | 3 商家、12 调查、约 1200 消息、约 300 条标注观点、30–50 张样品图 | 有 1200 条消息的回放种子，但没有标注 |
| 压测 | — | 无任何压测脚本 |

## 评测指标体系

共 5 类指标。"目标"一栏：设计文档已有的照搬；其余标为"基线后定"，测出基线再定，避免拍脑袋。

**1. 质量：结论对不对**

| 指标 | 怎么算 | 目标 |
| --- | --- | --- |
| 观点提取 macro-F1 | 按极性×属性（面料、做工、价格…）与人工标注对比，每类 F1 取平均，附混淆矩阵 | ≥ 0.80 |
| 反馈归因准确率 | 模糊反馈（"这款好看"）归到正确款式/版本的比例 | ≥ 85% |
| 建议正确率 | Agent 给的 PRODUCE / REVISE / TRIAL / HOLD 与标注答案一致的比例 | 基线后定 |
| 引用有效率 | 引用的证据 ID 中真实存在且属于本次调查的比例 | 100% |
| 引用相关率 | 引用的证据确实支持结论的比例（人工抽检或模型裁判 + 人工复核） | 基线后定 |
| 关键证据召回率 | 标注为"必须引用"的证据被引用到的比例 | 基线后定 |
| 稳定性 | 同一案例跑 5 次，建议一致的比例 | 基线后定 |
| 检索 Recall@5、MRR | 标注查询的相关片段有多少在前 5 条、第一条相关的排名 | 基线后定 |

**2. 效率：跑得快不快**

| 指标 | 怎么算 | 目标 |
| --- | --- | --- |
| 每个 Run 的轮数 | `agent_turn` 计数，看均值和分布 | 基线后定（上限 8） |
| 每个 Run 的工具调用数 | `tool_invocation` 计数 | 基线后定（上限 16） |
| 无效工具调用率 | 参数错误、被拒、同参数重复调用的比例 | 基线后定 |
| 端到端耗时 p50 / p95 | Run 创建到终态 | 基线后定 |
| 单轮模型耗时 p50 / p95 | 每次模型调用的请求到响应 | 基线后定 |
| 系统自身开销 | 端到端耗时 − 模型耗时 − 工具耗时（排队、数据库、上下文构建） | 基线后定 |
| 取消确认时延 | 发出取消到 Run 进入 CANCELLED | 基线后定 |

**3. 成本：花了多少钱**

| 指标 | 怎么算 | 目标 |
| --- | --- | --- |
| 每个 Run 的 token（输入/输出分开） | `usage_ledger` 汇总 | 基线后定 |
| 每个 Run 的花费 p50 / p95 | 按实际单价计算 | 月度总额 ≤ ¥300 |
| 输入 token 随轮数的增长 | 第 1–8 轮各自的输入 token | 基线后定 |
| 预留准确度 | 实际用量 ÷ 预留量 | 接近 1 |

**4. 可靠性：稳不稳**

| 指标 | 怎么算 | 目标 |
| --- | --- | --- |
| Run 成功率 | SUCCEEDED ÷ 全部 | 基线后定 |
| 失败原因分布 | 证据校验失败、超轮数、超时、模型报错、答案解析失败各占多少 | 基线后定 |
| 租约换手次数 | 每个 Run 的 `lease_epoch` 增长次数，正常情况下应为 1 | 1 |
| 限流重试次数 | 模型返回 429 的次数 | 基线后定 |

**5. 安全：硬门槛**

提示注入改变行为、跨租户泄露、伪造证据通过校验、截止后产生副作用，这四项必须是 0。现有安全测试已覆盖大部分，评测时补上"对抗案例"的通过率即可。

**P0 补充说明（批次 A 落地后）**

- 回归测试：`RuntimeBatchATest`（租约 4 秒、续租 500ms、慢调用 6 秒；轮询等待，无固定 sleep）和 `TokenEstimatorTest`，都在默认构建里跑。
- "租约换手次数"指标：`lease_epoch` 除了租约过期重认领，HITL 审批后的 resume 和取消也会让它 +1。统计时要按事件区分，不能直接用 `lease_epoch - 1`。
- 默认 8000 的 research 预算按新的预留方式，估计 4 轮左右就会被拦下（假设每轮新增约 650 token 的工具结果；新增 300 到 1000 token 时是 5 到 3 轮）。要跑满 8 轮大约需要 24000。评测前用 `CRAFTPILOT_RUNTIME_RESEARCH_TOKEN_BUDGET` 调高，并在报告头部记录所用的预算。以上数字是估算，以 P0-5 埋点后的实测为准。

**待办：事务内吞掉唯一键冲突（批次 A 排查时发现）**

PostgreSQL 的事务里只要有一条语句报错，整个事务就被标记为已中止；即使代码 catch 了 `DuplicateKeyException`，最后的 COMMIT 也会被静默回滚，而且不抛任何异常。批次 A 已修好 `BudgetService.settleModel`，下面几处是同样的写法：

| 优先级 | 位置 | 状况 | 计划 |
| --- | --- | --- | --- |
| 已修 | `OutboxDispatcher.java:162` | 回执插入单独占一个事务，吞掉重复键时静默回滚的只有这条重复回执，ack 在另一个事务里照常执行，所以没有可观察的 bug（原先说"状态更新丢失"不准确）。已改为 ON CONFLICT DO NOTHING，防止以后合并事务后出问题 | fix/outbox-idempotent（PR #10），配了回归测试（不是复现测试） |
| 已修 | `CheckpointService.java:40` | 调用点外面都没有事务，但 append 本身带 @Transactional，重复 transition_key 时 catch 里的查询会报 25P02，重复调用直接失败 | fix/outbox-idempotent（PR #10），配了复现测试 |
| 低 | `GroupService`、`SurveyService`、`TriggerService`、`CatalogService` | 业务层的同类写法，不在 Runtime 范围内 | 逐个确认是否在事务内 |

## 测试数据集与场景

一共准备 4 套数据，全部放在 `backend/src/test/resources/eval/` 下，用 JSON 或 CSV 保存并带版本号。规模按设计文档的要求来定，但先做一个小版本跑通整条流程，再逐步加样本。

| 数据集 | 内容 | 标注什么 | 第一版规模 | 完整规模 |
| --- | --- | --- | --- | --- |
| 观点标注集 | 从 1200 条回放消息里抽取的群聊消息 | 极性（正/负/中性）、属性（面料、做工、尺寸、配色、价格、整体）、指向的款式和版本 | 100 条 | 约 300 条 |
| 检索标注集 | 商家可能问的问题，如"V2 面料的负面反馈" | 每个问题对应的相关证据 ID | 20 个问题 | 50 个问题 |
| 调研案例集 | 一次完整调查：款式、样品图、反馈、投票 | 标准建议（PRODUCE/REVISE/TRIAL/HOLD）、必须引用的关键证据、允许的合理答案 | 10 个 | 20–30 个 |
| 对抗案例集 | 刻意设计的难题 | 期望行为（应拒绝、应 HOLD、应失败） | 10 个 | 20 个 |

实际的 v1（批次 B）比上表小：观点 50 条、调研案例 10 个、对抗案例 5 个，检索标注集还没做；全部是手工编写的模拟数据，没有从回放消息里抽取。说明和标注规则见 `backend/src/test/resources/eval/README.md`。

调研案例要覆盖这几种情况，否则建议正确率没有区分度：

- 反馈明显正面 → 应 PRODUCE
- 整体喜欢但某个属性集中差评（如面料硬）→ 应 REVISE，并引用那些差评
- 喜欢的人多但购买意愿低 → 应 TRIAL
- 反馈太少或意见对立 → 应 HOLD
- V1 和 V2 的反馈混在一起 → 不能把 V1 的差评算到 V2 头上

对抗案例包括：反馈里夹带"忽略之前的指令"的注入文本、MCP 工具返回内容里的注入、没有任何证据的调查、引用其他商家证据 ID 的伪造答案。

标注注意事项：

- 标注规则先写成一页说明，属性的定义、模糊情况如何处理都写清楚。
- 如果能找到第二个人，双人标注其中 30 条，算一致率；一致率就是这个任务的可达上限。
- 按 7:3 切分：7 成用来调提示词和规则，3 成只在最终评测时用，平时不看。

## 评测工具与实现

评测分三层。每层的运行方式、花费和频率都不同，所以拆开做，不要塞进每次提交都跑的 CI。

| 层 | 测什么 | 模型 | 怎么跑 | 频率 |
| --- | --- | --- | --- | --- |
| 组件评测 | 观点提取 F1、检索 Recall@5 | 规则版不调模型；模型版和 Embedding 用真实接口 | JUnit，打 `@Tag("eval")`，直接调 `OpinionExtractor`、`RetrievalService` | 改了提取或检索时 |
| 端到端 Agent 评测 | 建议正确率、引用、轮数、耗时、成本 | 真实模型 | 对每个案例建一个 Ticket，等 Run 结束，再从数据库采集指标 | 改了提示词、模型或 Runtime 时 |
| 性能压测 | 吞吐、p95、租约换手、系统开销 | 桩模型，固定延迟（如 3 秒）和固定工具调用剧本 | k6 压 HTTP 接口；Worker 吞吐用 JUnit 并发提交 N 个 Run | 修完 P0 后、每次性能优化后 |

**端到端评测的运行器**

1. 读入案例集，用现有的业务接口建好商家、款式、调查和反馈（可以复用 `R5TestSupport`）。
2. 触发研究 Run，轮询到终态。每个案例跑 3–5 次，用来算稳定性。
3. 用 SQL 从 `agent_run`、`agent_turn`、`usage_ledger`、`tool_invocation`、`research_report` 采集每个 Run 的指标。
4. 与标注答案比对，每个 Run 输出一行到 `eval-runs.csv`。
5. 写一个 Python 脚本读 CSV，算均值、p50/p95、混淆矩阵，生成 Markdown 报告；两次评测的报告可以直接对比。

每次评测的报告头部记录：数据集版本、提示词版本、模型名和温度、git commit、机器配置、本次总花费。

**结论质量怎么判**

- 建议是否正确、关键证据是否被引用：直接和标注比，不需要人判。
- 引用是否真的支持结论、摘要写得好不好：用另一个模型按评分标准打分（LLM-as-judge），再人工抽查 20%，算人机一致率。一致率低就不采信模型打分。

**压测场景**

- 群聊突发：k6 模拟调查截止前几分钟的集中发消息和投票，记录 TPS、p95/p99、WebSocket 广播延迟。
- Outbox 积压：突发后事件从写入到发出的延迟，以及消化完积压的时间。
- Worker 吞吐：同时提交 10 / 50 / 100 个 Run，记录每分钟完成数、排队时间、租约换手次数。
- 资源观察：数据库连接池只有 8 个连接，重点看连接等待时间（Hikari 自带指标）。

指标采集：开启 Actuator 的 Prometheus 端点，本机用 Docker 起 Prometheus 和 Grafana 看曲线，压测时截图留证。

## 执行步骤

顺序是：先让指标可信，再测基线，然后一项一项地优化。第 3 步的基线报告是之后所有对比的参照。

1. **准备：埋点、数据集、评测运行器**
   - 补耗时埋点（P0-5）；标注第一版数据集
   - 写运行器和报告脚本，先用桩模型跑通整条流程
2. **修 P0-1 到 P0-4**
   - 租约续期、预留额度、失败原因、单价配置
   - 每项配一个回归测试，确认现有测试仍全部通过
3. **测基线 v0**
   - 组件评测 + 端到端评测，每个案例跑 3–5 次
   - 报告存档，之后所有改动都和它对比
4. **P1 逐项优化**（每改一项，复测一次）
   - 观点提取、上下文、结构化输出、提示词、并行工具
   - 一次只改一个变量
5. **性能压测**
   - 群聊突发、Outbox 积压、Worker 吞吐
   - 用桩模型，记录 p95 和瓶颈在哪
6. **汇总报告**
   - 前后对比总表、成本统计
   - 更新 README，写进简历

第 4 步里，建议先做 P1-1（观点提取）和 P1-2（上下文）：前者直接决定结论质量，后者直接决定成本，改进幅度也最容易看出来。
